# pdf.jpgToPdf@1

Combines one or more JPG/JPEG images into a single PDF, one image per page, in the order given. This is
the whole operation — no cropping, no fit-to-page scaling, no image editing, and no EXIF-orientation
rotation (see the engine README's "page size and orientation" section for why).

## Input

| Field | Type | Rule |
|---|---|---|
| `files` | array of `{ name: string, bytes: Uint8Array }` | The JPG images to convert, in page order. `name` identifies a file in error details only. |
| `outputFileName` | string, optional | User-entered output name, normalized by `sanitizeOutputFileName` (see below). |

No `params` are needed for this operation's first version.

## Output

| Field | Meaning |
|---|---|
| `bytes` | The generated PDF's raw bytes. |
| `fileName` | The normalized output file name (`images.pdf` by default). |
| `imageCount` | Number of images converted (always equal to the resulting page count, one image per page). |

## Validation, in order

1. **Image count.** Zero images is `PDF_JPG_NO_FILES_SELECTED`; more than 50 is `PDF_JPG_TOO_MANY_FILES`.
2. **Per image, in given order:** size over 15 MB is `PDF_JPG_FILE_TOO_LARGE`; no JPEG SOI signature at
   byte 0 is `PDF_JPG_INVALID_FILE_TYPE`. Both checks run before any image is decoded.
3. **Combined total** over 75 MB is `PDF_JPG_TOTAL_SIZE_EXCEEDED`, checked once every individual image has
   passed its own size and type check.
4. **Per image, while embedding:** an image that has a valid JPEG signature but fails to decode (a
   corrupted or truncated file) is `PDF_JPG_UNREADABLE`.
5. **Page creation and the final save step** fall back to `PDF_JPG_CONVERSION_FAILED` for any unexpected
   failure once every input image has already embedded successfully.

Every error identifies which image caused it (`path: files.<index>`, `details.name`) except the three that
are not about any one image (`PDF_JPG_NO_FILES_SELECTED`, `PDF_JPG_TOO_MANY_FILES`,
`PDF_JPG_TOTAL_SIZE_EXCEEDED`).

## Warnings

Every successful result carries four standing notices, unconditionally (`warnings.ts`):
`PDF_JPG_VERIFY_OUTPUT`, `PDF_JPG_LARGE_OR_MANY_MAY_FAIL`, `PDF_JPG_QUALITY_DEPENDS_ON_SOURCE`,
`PDF_JPG_AUTHORIZED_USE_ONLY`.

## Page size

Each page is created at exactly the embedded image's own pixel dimensions
(`doc.addPage([image.width, image.height])`), then the image is drawn to fill it completely. There is no
A4/Letter fitting and no scaling — the simplest, most predictable, and most deterministic option. See the
engine README for the documented EXIF-orientation limitation this implies.

## Determinism: a fixed creation/modification date

Same non-suppressible `pdf-lib` date-stamping behavior as `pdf.merge@1` (see the engine README): both
dates are set explicitly to the Unix epoch right after `PDFDocument.create()`.

## A `pdf-lib` bug this operation works around

`toEmbeddableJpegBytes()` copies JPEG bytes into a fresh, zero-offset `Uint8Array` before calling
`embedJpg`, working around a real bug in `pdf-lib`'s `JpegEmbedder` that misreads the SOI marker for any
`Uint8Array` that is itself a slice of a larger buffer. See the engine README for the full explanation.

## Output file name normalization

`sanitizeOutputFileName` (in `file-name.ts`) is identical in behavior to `pdf.merge@1`'s, except the
default name is `images.pdf`: trim whitespace, strip unsafe characters, normalize the `.pdf` extension,
and fall back to the default if nothing usable remains.

## Limits (founder-approved, `limits.ts`)

| Limit | Value |
|---|---|
| Maximum size per image | 15 MB |
| Maximum combined size | 75 MB |
| Maximum number of images | 50 |

These are Phase 1 starting points, stated honestly to the user by the tool built on this operation, and
may be revised after real-world testing.

## Fixtures

Binary test JPEGs live in `fixtures/files/`, all hand-built minimal baseline JPEGs (no photo library or
image-encoding dependency is available or permitted in this engine):
- `small-square.jpg` — an 8×8 solid mid-gray JPEG (one MCU, DC-only, no AC coefficients).
- `wide.jpg` — a 16×8 solid gray JPEG (two MCUs), a different size and gray level so a unit test can tell
  images and their resulting pages apart.
- `corrupted.jpg` — `small-square.jpg` truncated after its headers: a valid SOI signature, but no scan
  data for `pdf-lib` to decode.
- `not-a-jpg.txt` — a plain text file, to exercise the file-type check.

The YAML fixtures cover every case that reduces to a scalar comparison (`imageCount`, `fileName`) or a
typed error. Cases needing a structural check on the generated bytes (page order/size, a forced save
failure) are unit tests in `jpg-to-pdf.test.ts` instead. Size- and count-limit cases
(`PDF_JPG_FILE_TOO_LARGE`, `PDF_JPG_TOTAL_SIZE_EXCEEDED`, `PDF_JPG_TOO_MANY_FILES`) are also unit tests,
using small in-memory byte arrays rather than committing real oversized JPEGs — these checks run before
any decoding, so content beyond the checked length/signature does not matter.
