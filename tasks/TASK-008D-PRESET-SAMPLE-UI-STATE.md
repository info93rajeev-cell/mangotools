# TASK-008D — Preset Sample UI State

## Lane

platform

## Size

S

## Goal

Allow a preset sample to initialise UI-only form state separately from the strict input sent to its
engine operation.

The additive preset shape is:

```yaml
samples:
  example:
    titleKey: example.sample
    input:
      grossSellingPrice: "1000"
      productCost: "500"
      marketplaceFees: "100"
    uiState:
      showAdvancedCosts: true
```

`sample.input` remains engine input. `sample.uiState` is optional form state for fields declared
`uiOnly: true` in the same resolved preset. UI state never becomes engine input or params.

## Why this is a platform task

The repository assigns all required implementation surfaces to the `platform` lane:

- `schemas/` owns the preset data shape;
- `scripts/` validates and resolves presets and samples;
- `packages/runtime/` creates form state and engine requests.

No engine, tool, preset, or shared UI component needs to change in this prerequisite.

## In scope

Authorize the smallest coherent implementation of optional `samples.<id>.uiState` across:

- the preset schema and generated schema artefacts;
- generator validation for UI-state keys and values;
- resolved preset/runtime types derived from the schema;
- runtime sample-state loading;
- focused schema, generator, and runtime tests;
- brief preset documentation or comments required to explain the boundary.

Generated files must be regenerated by the normal repository workflow and must not be edited by
hand or committed when the repository excludes them.

## Contract

### `input`

- `input` remains required and contains engine-backed input only.
- It continues to be validated against the selected operation's strict input schema.
- Its execution and fixture semantics do not change.
- A UI-only key in `input` remains invalid; this task must not weaken strict engine validation.

### `uiState`

- `uiState` is an optional keyed map on an individual sample.
- Omitting it is identical to the current sample behaviour.
- Every key must name a field in the same resolved preset.
- Every referenced field must declare `uiOnly: true`.
- Values must be valid for that field's declared kind, fixed options, and custom-value policy.
- The implementation must reuse the repository's existing field-value and option conventions rather
  than create a second incompatible value language.
- The initial implementation is declarative state only. It cannot run expressions, scripts,
  callbacks, actions, or arbitrary commands.

### Runtime application

When a user applies a sample, the runtime must:

1. begin from the preset's normal defaults;
2. overlay `sample.input` onto engine-backed form fields;
3. overlay `sample.params` through the existing params path, when present;
4. overlay `sample.uiState` only onto validated UI-only fields;
5. build the engine request through the existing request builder, which excludes all `uiOnly`
   fields.

The separation must hold even if an author uses the same-looking value in both maps. `uiState` is
never merged into `input`, `params`, operation fixtures, working data, or result values.

### Reset

Reset must continue to use the preset's normal defaults. It must clear sample-applied `uiState` and
must not preserve a sample-opened disclosure or helper control unless that state is itself the
preset default.

### Copy, print, share, analytics, and logging

- Existing copy, print, and result payloads remain based on engine results and their established
  presentation data.
- Existing share behaviour must not reinterpret `uiState` as engine data. If share state already
  serialises form UI state separately, it may continue to do so only through that existing boundary.
- No analytics event, property, logging, storage, or network behaviour is added.
- No user-entered content may be emitted to analytics or logs.

## Validation behaviour

Use existing schema/generator issue conventions and file/data paths. Do not add a public engine error
code because invalid sample authoring is a build-time preset problem, not a user-input operation
error.

Generation must fail deterministically when:

1. `uiState` names a field that does not exist in the resolved preset;
2. `uiState` names a field that is not marked `uiOnly: true`;
3. a value is incompatible with the referenced field's declared kind;
4. an enum value is not one of the field's supported options;
5. a custom enum-or-number value is supplied where that field does not allow custom values.

Validation messages must identify the sample and offending `uiState` key through the existing issue
path mechanism. Unsupported values must not be silently coerced to a different option.

## Backward compatibility

- Existing samples containing only `titleKey`, `input`, and optional `params` remain valid and behave
  byte-for-byte as before.
- `uiState` is optional, so existing preset YAML does not require migration.
- `presetVersion` remains `1`; this is an additive optional authoring capability, not a breaking
  schema revision.
- Existing presets, generated registry consumers, fixtures, and operation contracts do not change.
- The resolved preset may expose optional `uiState` only inside sample definitions; consumers that
  do not apply samples need no new behaviour.

## Implementation boundaries

The later implementation may touch only the minimum relevant platform files, expected to include:

- `schemas/src/preset.ts`;
- `scripts/generate/preset-checks.ts` or a narrowly named adjacent validator module;
- `packages/runtime/src/tool-input.ts`;
- colocated focused tests for those modules.

It must not require a `packages/ui` change. If implementation discovers that a UI-component contract
must change, stop and create a separate `ui`-lane task rather than expanding TASK-008D.

## Out of scope

Do not include:

- the Seller Profitability preset or tool implementation;
- changes to TASK-008C;
- changes to PR #99 or its branch;
- marketplace rates, fee tables, platform-specific seller knowledge, or HSN/GST data;
- network access, product URLs, scraping, or live refresh;
- adapters, authentication, Firebase, storage, or new dependencies;
- engine operation or fixture changes;
- general disclosure or calculator redesign;
- arbitrary sample scripting or lifecycle hooks;
- persistence of sample UI state beyond existing form-state behaviour.

## Acceptance tests for the later implementation

Add focused coverage proving:

1. a legacy sample with `input` only remains valid and applies exactly as before;
2. a sample with valid `uiState` passes schema and generator validation;
3. valid UI state opens or enables an existing disclosure controlled by a `uiOnly` field;
4. `uiState` is absent from the request sent to the engine;
5. an unknown `uiState` key is rejected with its sample path;
6. a key referencing a non-`uiOnly` field is rejected;
7. an invalid field value or unsupported enum option is rejected;
8. reset restores normal preset defaults after applying a sample;
9. every existing preset and sample remains valid without migration;
10. `pnpm verify` and architecture validation pass.

Keep the matrix minimal. Tests should prove the schema/validation/runtime boundary without creating a
tool-specific or engine-fixture duplicate.

## TASK-008C dependency

TASK-008C is blocked only on this missing sample UI-state capability. After the TASK-008D
implementation is merged, TASK-008C may resume with its marketplace-style deterministic sample and
advanced-field disclosure without marketplace data, network access, or shared-UI expansion.

Do not modify `tasks/TASK-008C-SELLER-PROFITABILITY-TOOL.md` in this contract PR.

## Governance

This is a backward-compatible addition to the existing preset authoring schema and runtime. The
`platform` lane is restricted and requires deep founder review. No separate ADR is required by the
current repository rules because this task does not change an engine operation, dependency direction,
security boundary, persistence model, or accepted architectural decision. This approved task is the
required contract before implementation.

If review determines that preset sample state is an externally supported public API rather than an
internal additive authoring contract, stop before implementation and draft an ADR; do not infer that
classification during coding.

## Acceptance criteria

- The contract adds only optional `sample.uiState` semantics.
- `sample.input` stays strict engine input.
- `uiState` accepts only valid values for fields marked `uiOnly` in the same resolved preset.
- `uiState` can never reach engine input or params.
- Legacy samples require no migration and retain existing behaviour.
- Reset restores normal defaults.
- Copy, print, share, analytics, logging, storage, and network boundaries do not expand.
- No engine, preset, tool, UI, dependency, or generated-file source is changed by the contract PR.
- The later implementation remains one `platform`-lane, size-S task.
